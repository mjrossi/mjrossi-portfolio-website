## Upfront disclaimers

Yes, I vibe coded a substantial amount of the Atlas. No, I'm not a diehard AI evangelist or doomer. I try to recognize where AI is helpful (repetitive tasks, extra analysis), and where we should be concerned (energy and environmental impacts).

"OK, so what are you writing here?" would be a valid question to ask.

In a social media ecosystem filled with absolutes and binaries, the intention of this post is to be upfront about how I used Claude Code as a tool to help me write the Atlas: where AI was helpful and effective, where there were shortcomings, and hopefully an example of where a modern software engineer can use AI, but where that AI is only as effective as the engineer behind the keyboard.

## AI for the code

### The Go API

I'm primarily a backend engineer, so I've designed my fair share of APIs, build tools, low-level data layers, integrations, etc. This is where I could be the most picky and explicit about how I wanted the code built. It was also my natural starting point, since I wanted the API to drive everything, including the inevitable front end, and future ability to allow users to directly integrate with the API.

I knew I wanted Go, but I also wanted to see how Claude would fare, so I began a brainstorming session. My prompt was explicit in ask, but not in tech stack (at first). I directed that I wanted an API that would support the ability to both power a front end website, but also be directly accessible by `curl`. I started with the most simple endpoint, `/lookup`, since I could use that as a simple complete slice of a working bit of functionality. I didn't want to worry about the data quite yet, so I directed it to hard-code `11217` (my zip code) with one organization.

It suggested that I write it all in Node / JavaScript. I disagreed. I'll admit that it was partially out of preference, but I also wanted an API that would scale, use a language that had better multithreading support, and a static typechecker. So... I gave it all of that, and it was at this point I also explicitly said I wanted Go. To me, this was the first trap that can burn folks that don't have a software engineering background when they try to vibe code. There is nothing wrong with Node for this task, but there are reasons not to take that first suggestion at face value.

At this stage, it started proposing a plan for Go. There was a lot of back and forth; I was explicit in my input. From this one endpoint, we needed initialization logic, managing the configuration of the application, how and where it was going to be deployed, etc. Could I have just taken its recommendation? Yes. But after thirteen years of writing code, and very recently writing an extremely robust application in Go, I had my own ideas of how I wanted to do this, so I was explicit with the robot in my asks. I split the ask into subagents, acting as a bit of a project manager, product owner, and software architect in one go.

And it delivered! By being extremely detailed in my input, leveraging my knowledge, we ended up with an endpoint and structure of code I was pleased with. Over time, we added more layers, more endpoints, a `just` file and `mise` for managing tooling. If I was unclear or didn't have a strong preference, there was the back and forth, and I'd explicitly push the AI to look at community guidelines on making good choices.

Another area where the human matters — those community guidelines exist because humans who care about good code quality are out there, and publish their work.

### The React SPA

This is where I knew I was going to run into more difficulty. I _don't_ have strong front end experience. My JavaScript knowledge at the start of this application is basically "jQuery is definitely not a thing anymore, right?". Beyond a few small edits to larger front end framework applications, it was not a strong suit for me.

Neither is design, so I used Claude Design to help draft the look of the front end before writing any code or deciding on any framework. I'd already done an iteration of this on my personal blog and website, so I used that as a starting point. The core principles are the same though: be explicit in your input, push back, review, and eventually the output will be what you're happy with. I was also impressed with the fact it could produce handoff materials to Claude Code to go ahead and implement the front end code, which I definitely took advantage of.

As for the front end itself, I was direct in my initial prompts — I have a lot of experience as a backend engineer, minimal front end, but have dabbled in HTML, CSS, JavaScript, TypeScript, Node, etc. I leaned much more on the AI, but was explicit that I needed advice. I knew my high-level asks: easy to maintain; no stored state, consuming everything from the API; hosted on Cloudflare; thoroughly tested; and open to community input. It provided a couple of solutions, but ultimately I went with the tried and true React solution.

From here, I built the first iteration of the UI that consumed that single `/lookup` endpoint from before. As with the backend, this single slice was a deliverable and something that showcased a working prototype that could be iterated on over time. And as before, it delivered. I now had a monorepo with two separate but connected pieces: a backend API in Go, and a front end app in React consuming that Go API. Hurrah!

### Fleshing out more features

Thinking like a product manager was really valuable here, because I've seen how useful it can be to just ship something that works. It doesn't need all the features ready. It doesn't need to be perfect. It just needs to show the basic structure and functionality works. This did it.

From that point on, I could work on each end in parallel, and use the other as a way to validate the contract. Add a new endpoint with a front end to consume, ensure it worked. Make changes on the front end, know that the backend was stable. I directed the AI to write an OpenAPI spec, so we were working with hard contracts that future agents — and me, and other contributors — could rely on. I always wanted to ensure that at the end of the day, nobody was going to feel stuck if they didn't have an AI robot to lean on to look at, review, or contribute to this code. To that end, specific documentation passes, tooling passes, thorough and well-written `just` commands, were always done in between new feature work or bugfixes.

Eventually it got to the point where we needed real data to work with.

## AI for the data

### The region graph

Cities are complex. Boundaries aren't always static. This was a fascinating portion of this project because it directly tied into the urban planning field, the very thing I'm pivoting my career into.

I started with the United States — it's what I know the best, right? I wanted zip codes to be the anchor, but learned quickly that zip codes aren't perfect. Those zip codes need to map to something. I knew about MSAs, but advocacy is local — 11217 is Brooklyn, but it's also Park Slope, but Park Slope isn't a hard defined border. Brooklyn is NYC, but if you type in 11217, that's also part of the New York - New Jersey - Connecticut MSA. But what if you're in CT but not part of the defined NY Metro?

Just from that paragraph, you can see how complex this was going to get. So... I did a Claude brainstorming session. I said "let's start by modeling New York City, Chicago, and San Francisco." These are places I knew well enough that I knew the brainstorming would be valuable in defining an initial draft, but I could push back if something didn't make sense. I didn't want to just hard code — that's not going to scale. I didn't want to include national orgs as an editorial decision. So, a directed acyclic graph (DAG) was built.

You can read in thorough detail [here](https://github.com/mjrossi/urbanist-atlas/blob/main/docs/region-graph.md) but for a high level summary:

The core idea is to stop thinking of a location as a fixed set of tiers — city, county, metro, state — and instead model geography as a graph. Every region is a node (a borough, a city, a metro, a state, a transit district, a multi-state coalition), and each node just declares its parents. A postal code anchors to the smallest region I've curated for it, and a lookup walks up the graph from there, collecting every region above it and the advocacy orgs attached to each. That's what makes typing in 11217 return Brooklyn-specific groups, citywide NYC groups, and New York State groups all at once, in the right order. The graph shape is also what lets the messy cases work without special-casing them one by one: NYC's metro spanning three states without leaking New Jersey orgs into a Brooklyn search, Chicago's transit district covering six counties but only one state, or a city-state like Berlin that's technically a Land but functions as a city. And because none of it is hard-coded to the US, the same model already stretches to Canada, with room for Portugal, Germany, and more as I add them.

I ran specific agents to stress-test the model as it was being built. In doing so, odd edge cases were found — Washington, D.C., for example, which is not a state (but should be...), and often sits right alongside parts of MD and VA. Connecticut, which recently re-architected its metropolitan area boundaries (after the 2020 Census). Handling rural zip codes correctly so they map to their parent state.

Overall, I was extremely proud of the region graph design and this was a great example of using AI along with my own knowledge of cities to build an adaptable data model. I learned a lot working with these data sets.

### Cataloging the organizations

Cataloging hundreds of organizations on my own, across thousands of postal codes in two countries is the sort of task that would have taken weeks or months in the time before AI. The fact that I could do it (along with the rest of this project) in a little over a month of work is remarkable. That said, the data had to be accurate. It had to be verified.

The first bit was deciding exactly what organizations I wanted to include, so I defined a set of criteria that was at the forefront of any request to AI (full list [here](https://urbanistatlas.com/about)).

1. Geographic focus (the best advocacy happens locally)
2. Active advocacy (no inactive orgs; some activity within the last 12 months)
3. On-topic (transit, safe streets, etc.)
4. Government agencies, consultancies, and non-advocacy orgs are excluded (focus on advocacy)
5. Housing & YIMBY are excluded (tight focus)

So using the rules outlined above, here is the typical workflow for adding new organizations.

1. Prompt: "Please do a deep dive into organizations that are focused on advocating for safe, sustainable, and human-focused city design and transportation. Ensure that organizations follow the editorial rules defined. Comb through social media presence to determine activity. Ask me if you're unsure about a specific org."
2. Prompt (new agent): "Review all of the orgs found in the recent pass. Ensure they meet the criteria. Check the websites and social media presence for activity". Once that was done, I would review all the orgs myself, and also use a custom-built `just` command that spins up a Docker container with a basic Linux image, connects to a VPN (for safety), and then hits each URL we define and outputs a report if any don't work or return spam / parked domain results, etc. and then manually exclude those orgs.
3. Prompt: "Do another pass to look for orgs in `<region>`, seeing if we missed any or falsely flagged any that we should exclude based on the criteria." After this completed, I'd do another review step.

### Did it hallucinate?

Yes, occasionally. It didn't make up organizations — I think my input was strong enough to avoid that — but it did guess at URLs (that didn't exist), or provide some metadata that wasn't accurate. Fortunately, the combination of human review and subsequent agent reviews caught these. It was also at this point in the process that I decided to introduce a submission desk, so I could get a report if anyone found anything wrong.

Advocacy is human. Cities are human, and only exist as the incredible, culturally diverse places they are because of the people who live in them. This work is focused on making our cities better places to live. I never forgot that, no matter how many interactions I had with Claude.

Cities are living, breathing organisms that are unique. No predictive text generator is going to be able to fully understand the specific nuances of a city the way I only can after spending time there, talking to people, listening to their specific stories. So don't rely on AI — allow and encourage people to chime in, submit feedback, and tell us about their home.
