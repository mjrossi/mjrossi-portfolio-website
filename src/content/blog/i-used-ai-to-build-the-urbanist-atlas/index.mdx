This post has been stewing for the last month, in-between all of the aspects that go into an international move (which could be its own post someday) — my wife Hilary and I have relocated to Lisbon, Portugal, in preparation for my first year in the EIT Urban Mobility Master's program (Sustainable Urban Mobility Transitions) at Instituto Superior Técnico.

[The Urbanist Atlas](https://urbanistatlas.com) — a directory of local safe-streets and transit advocacy organizations, searchable by ZIP or postal code — has been live for about six weeks now, which feels like enough time to reflect on what worked, what didn't, and where I still had to step in instead of letting Claude run on its own. That six weeks of reflection became a three-part series. This first post covers the code: how I used Claude Code as my "coding assistant" while greenfielding the project. The second covers the data — modeling cities as a graph, generating that graph from federal datasets, and cataloging the organizations. The third steps back, with tips and broader, non-technical thoughts about AI.

## Upfront disclaimers

Yes, I vibe coded a substantial amount of the Atlas. But "vibe coding" has gotten so overused it's practically lost its meaning, and loaded enough to make people roll their eyes, so it's worth saying what I actually mean by it: AI generated a lot of code, but I was the one specifying architecture, reviewing the generated changes, writing and running tests, validating the data, and making the calls when the AI's first answer wasn't the right one. I'm neither an AI evangelist nor an AI doomer — I try to recognize where AI is helpful (repetitive tasks, extra analysis), and where we should be concerned (energy and environmental impacts).

"OK, so what are you writing here?" would be a valid question to ask.

In a social media ecosystem filled with absolutes and binaries, the intention of this post is to be upfront about how I used Claude Code as a tool to help me write the Atlas: where AI was helpful and effective, where there were shortcomings, and hopefully an example of where a modern software engineer can use AI, but where that AI is only as effective as the engineer behind the keyboard.

## AI for the code

### The Go API

I'm primarily a backend engineer, so I've designed my fair share of APIs, build tools, low-level data layers, integrations, etc. This is where I could be the most picky and explicit about how I wanted the code built. It was also my natural starting point, since I wanted the API to drive everything, including the inevitable frontend, and future ability to allow users to directly integrate with the API.

I knew I wanted Go, but I also wanted to see how Claude would fare, so I began a brainstorming session. My prompt was explicit about what I wanted, but not about the tech stack — at first. I directed Claude to build an API that would support the ability to both power a frontend, but also be directly accessible by `curl`. I started with the simplest endpoint, `/lookup`, since I could use that as a complete slice of a working bit of functionality. I didn't want to worry about the data quite yet, so I directed Claude to hard-code `11217` (my zip code) with a single result: one advocacy organization, the kind of entry the Atlas is built to catalog.

It suggested that I write it all in Node / JavaScript. I disagreed. That was partially my preference, but I also had specific technical reasons: I wanted static typing, a straightforward concurrency model, and, practically, a language I'd already written a robust production application in recently. Node would have worked fine here too; that's not the point. The point is I had reasons, and I could articulate them. To me, this was the first trap that can burn folks who don't have a software engineering background when they try to vibe code: the danger isn't that AI will make a bad choice, it's that it'll make a perfectly plausible one you don't know enough to question.

At this stage, Claude started proposing a plan for Go. There was a lot of back and forth; I was explicit in my input. From this one endpoint, we needed to write the initialization logic, manage the application configuration, and settle the deployment target. Could I have just taken its recommendation? Yes. But after thirteen years of writing code, and very recently writing an extremely robust application in Go, I had my own ideas of how I wanted to do this, so I stayed just as explicit with Claude about the rest. Rather than hand all of that — initialization, configuration, deployment — to a single pass, I acted as a bit of a project manager, product owner, and software architect in one go, and split the work across three of Claude Code's subagents: one focused purely on the endpoint and API design, another on deployment and tooling (the `just` file and `mise` config that show up below), and a third whose only job was to review the first two against idiomatic Go and Go community convention.

And Claude delivered! By being extremely detailed in my input, leveraging my knowledge, we ended up with an endpoint and structure of code I was pleased with. Over time, Claude and I added more layers, more endpoints, a `just` file and `mise` for managing tooling. If I was unclear or didn't have a strong preference, there was the back and forth, and I'd explicitly push the AI to look at community guidelines on making good choices.

That's another place the human shows up in this story — those community guidelines exist because people who care about good code quality wrote them down and published them.

### The React SPA

This is where I knew I was going to run into more difficulty. I _don't_ have strong frontend experience. My JavaScript knowledge at the start of this application is basically "jQuery is definitely not a thing anymore, right?". Beyond a few small edits to larger frontend framework applications, it was not a strong suit for me.

The frontend was therefore a more interesting test of my thesis: I was delegating more of the implementation and design decisions precisely because I knew less.

I'm not a designer either, so I used [Claude Design](https://claude.com/product/design) — Anthropic's dedicated design product — to draft the look of the frontend before writing any code or deciding on a framework. I'd already done an iteration of this on my personal blog and website, so I used that as a starting point, responding to each draft, asking for a different layout or visual hierarchy, and iterating until the handoff document matched what I actually wanted. I was also impressed that Claude Design could produce handoff materials for Claude Code to go ahead and implement the frontend code, which I definitely took advantage of.

As for the frontend itself, I was direct in my initial prompts — I have a lot of experience as a backend engineer, minimal frontend, but have dabbled in HTML, CSS, JavaScript, TypeScript, Node, etc. I leaned much more heavily on Claude's input here, but was explicit that I needed advice, not just answers. I knew my high-level requirements: easy to maintain; no stored state, consuming everything from the API; hosted on Cloudflare; thoroughly tested; and open to community input. Claude provided a couple of solutions, but ultimately I went with the tried and true React solution.

From here, I built the first iteration of the UI that consumed that single `/lookup` endpoint from before. As with the backend, this single slice was a deliverable and something that showcased a working prototype that could be iterated on over time. And as before, Claude delivered: a real page that called the live endpoint and rendered a real result, not a mockup. I now had a monorepo with two separate but connected pieces: a backend API in Go, and a frontend app in React consuming that Go API. Hurrah!

### Fleshing out more features

Thinking like a product manager was really valuable here, because I've seen how useful it can be to just ship something that works. It doesn't need all the features ready. It doesn't need to be perfect. It just needs to prove the basic structure holds up. This did.

From that point on, I could work on the backend and frontend in parallel, using each side to validate the other. Add a new endpoint with a frontend to consume, ensure it worked. Make changes on the frontend, know that the backend was stable. I directed Claude to write an OpenAPI spec, so we were working with hard contracts that future agents — and me, and other contributors — could rely on. I always wanted to ensure that at the end of the day, nobody was going to feel stuck if they didn't have an AI robot to lean on to look at, review, or contribute to this code. To that end, specific documentation passes, tooling passes, thorough and well-written `just` commands, were always done in between new feature work or bugfixes.

That parallel work also settled how the two halves ship, which turned out not to be symmetric at all. The React app deploys to Cloudflare as static assets. The Go API runs on a single Fly.io machine — and "single" is load-bearing, not a cost decision. The submissions database is SQLite, which allows exactly one writer, and the queue that opens pull requests (more on that in the next post) lives inside the process itself. Scaling that machine horizontally wouldn't just be wasteful; it would quietly break both. The region data, meanwhile, is compiled directly into the Go binary, so changing the dataset means deploying the API rather than migrating a database.

### Where that leaves the code

Looking back at this half of the project, the pattern is consistent: Claude was fast and genuinely good, and every place it saved me real time was a place where I could already tell a good answer from a plausible one. I turned down Node for Go because I had thirteen years of reasons. I split the work across subagents because I knew what the roles were. I pushed back on the first draft because I knew what "well structured" looked like. None of that is the AI being weak — it's the AI being exactly as effective as the person directing it.

Which brings back the trap from earlier. The danger isn't that AI makes a bad choice. It's that it makes a perfectly plausible one you don't know enough to question. In the code, I mostly knew enough.

Eventually it got to the point where we needed real data to work with, and that's where the trap actually sprang. Cities don't fit neatly into hierarchies, government datasets disagree with each other about what year it is, and an organization that doesn't exist looks exactly like one that does until you check. That's the next post.
